Everyone has drawn the URL shortener: a hash, a table, a cache. It is still asked at every level, because the grade is on what comes after the diagram. This is a full reference solution at the Staff bar (L6/L7): theory with the mechanisms at work, a three-version design with C4 context, container and component views, every component one level down with the technology picked and the alternatives rejected (PostgreSQL vs Cassandra and DynamoDB, etcd vs ZooKeeper and Redis, Redis Cluster vs Memcached and Hazelcast, Kafka, Flink, ClickHouse), eight challenges that break it, and the build cost. 106 minutes, 643 numbered slides, with an interviewer, a candidate and a coach.

The thesis: a URL shortener is a read path with a write path attached. Codes must be unique without a lock per create and unguessable without a lookup, the redirect must be one memory read, and nothing else (counting, abuse, analytics) may stand between the click and the answer.

IN THIS VIDEO
• Estimates as arithmetic: why seven characters (3.5 trillion codes for 12 billion links), 4,000 redirects a second but 40 at the store, 7 of 20 milliseconds
• Theory: safety and liveness, six mechanisms, an options matrix for code generation with a pick (and an honest equal)
• Components and technologies: what each box runs on, how it is built one level down, and why each rival is ruled out
• Eight challenges: two servers and one code, codes that can be walked, one link at 40,000 clicks a second, 301 or 302, a takedown everywhere in five minutes, counting without slowing the redirect, a region lost, and how you would know
• The build cost and team split (marked AUX, the manager layer)

HOW TO USE IT
Run the round cold first. Then watch once straight through. On the second pass, pause after each interviewer question and answer it first. Slides badged AUX are the manager layer: skip them in a Staff round.
Captions: turn on CC (English, translatable). Every table and diagram is built up step by step, the way you would draw it at a whiteboard.
