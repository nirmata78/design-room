Theory · 1 of 6 · what it is
A map from a short, unique, hard-to-guess code to a long URL, answered in milliseconds from anywhere, that can be withdrawn everywhere within a stated time.
Theory · 1 of 6 · what it is not

Four things it is confused with

Not a hash function

Hashing the URL is one way to make a key. It is not the system, and it is not unique once truncated.

Not a cache

The map is the source of truth. A cache is a copy that may be wrong for a bounded time.

Not a secret

Seven characters can be sampled. A link that must stay private needs authentication.

Not a CDN

The edge is a layer that answers for us, and that we must be able to take back.

Theory · 2 of 6 · the two properties

State safety and liveness separately

Safety · must never happen

S1 Two different long URLs are given the same code.
S2 A withdrawn code is answered by any layer after the takedown bound.

Liveness · must eventually happen

L1 A create gets a code without waiting for another create.
L2 A redirect for a live code answers within the target, even at a viral peak or with the store down.
L3 Every click is eventually counted, with a stated, measured loss.

Theory · 4 of 6 · mechanism 1 of 6

Counter ranges plus base-62

Property it protects

S1 and L1.

How it works

Each create server leases a block of 1,000 IDs from an allocator in one conditional write, then hands them out locally and encodes each in base-62.

Failure it rules out

Two servers handing out the same code; a lock or a round trip on every create.

What it costs

Gaps when a server dies holding a range: harmless at 290× headroom. Codes are sequential, unless mechanism 2.

Theory · 4 of 6 · mechanism 2 of 6

A keyed permutation

Property it protects

Non-enumerability.

How it works

A small Feistel network over the code space with a secret round key, plus cycle walking to stay below 62⁷. A bijection: distinct in, distinct out.

Failure it rules out

Scrapers walking codes in order; codes that reveal how many links we create.

What it costs

A key to keep and rotate. It is not secrecy: private links still need authentication.

Technology · link store

PostgreSQL, sharded by code, a primary per region's slice

How it is builtlink(code char(7) PRIMARY KEY, …). A code maps to a shard by hash. Each region is the primary for the links it creates (its slice of the ID space) and holds asynchronous replicas of the others. Each primary has a synchronous standby in another zone. INSERT … ON CONFLICT (code) DO NOTHING RETURNING code.
OptionWhy it is chosen, or why not
PostgreSQL 16, 16 shards per regionPrimary key on the code is the unique constraint; one insert wins, the other gets no row back. 6 TB is boring for it; we know how it fails.
Cassandra / ScyllaDBFits the reads well. But uniqueness needs a lightweight transaction (IF NOT EXISTS), a Paxos round per insert, and its multi-region serial modes are easy to get wrong. Its strength, leaderless writes everywhere, buys us nothing at 400 writes a second.
DynamoDBA conditional put is exactly the constraint, in one region. Global tables resolve concurrent writes by last writer wins, so an alias created in two regions at once could succeed twice. Cloud lock-in too.
One big PostgreSQLWrites fit. 18 TB with replicas on one primary, one failure domain, and vacuum on a 12-billion-row table: no.
Background: building-blocks course, part 5 (replication) and part 6 (partitioning)

Technology · range allocator

etcd: a compare-and-set on a Raft log

How it is builtKey /alloc/{region}/next. A lease is one transaction: If(ModRevision(next) == r) Then(Put(next, n + 1000)) Else(Get(next)). Committed when a majority of the Raft group has it. No expiring lock, so no clock assumption and no fencing token: a crashed server just leaves a gap.
OptionWhy it is chosen, or why not
etcd, 3 nodes per region across zonesLinearizable compare-and-set by revision; survives one node; tiny load (0.4 leases a second). Often already run for Kubernetes.
ZooKeeperThe same guarantee (a conditional setData on the znode version, replicated by ZAB). An honest equal; rejected only for running a JVM ensemble for this alone.
Redis INCRBYFast, but replication is asynchronous: after a failover the new primary may not have seen the last INCRBY and hands out the same range twice. That breaks S1 silently.
Cassandra counter or LWTCounters cannot compare-and-set; an LWT works but ties create to the busiest store.
A PostgreSQL sequence (INCREMENT 1000)Durable and simple, a defensible choice. Rejected because creates would then depend on one link-store shard's fail-over.
Background: building-blocks course, part 2 §2.11 (leases and fencing) and part 3 (consensus, Raft)

How it is builtKey /alloc/{region}/next. A lease is one transaction: If(ModRevision(next) == r) Then(Put(next, n + 1000)) Else(Get(next)). Committed when a majority of the Raft group has it. No expiring lock, so no clock assumption and no fencing token: a crashed server just leaves a gap.
OptionWhy it is chosen, or why not
etcd, 3 nodes per region across zonesLinearizable compare-and-set by revision; survives one node; tiny load (0.4 leases a second). Often already run for Kubernetes.
ZooKeeperThe same guarantee (a conditional setData on the znode version, replicated by ZAB). An honest equal; rejected only for running a JVM ensemble for this alone.
Redis INCRBYFast, but replication is asynchronous: after a failover the new primary may not have seen the last INCRBY and hands out the same range twice. That breaks S1 silently.
Cassandra counter or LWTCounters cannot compare-and-set; an LWT works but ties create to the busiest store.
A PostgreSQL sequence (INCREMENT 1000)Durable and simple, a defensible choice. Rejected because creates would then depend on one link-store shard's fail-over.

resp, err := cli.Txn(ctx).

// lost the race: Else returned the new value and revision; try again
Why it worksThe compare on the revision makes leases disjoint. Inside a lease no coordination is needed; across leases none is possible to get wrong.

Runway, a replicated allocator, and the right failure

Runway

Lease the next block at half-used: 500 to 1,500 IDs in hand. At the 400/s peak over ten servers that is 12–37 s; at the 40/s average, two to six minutes.

A replicated allocator

Three etcd nodes across zones: losing one node is not an outage. 0.4 leases a second is no load.

A crashed server

Its unused IDs are skipped: a gap, not a collision.

If the allocator is down for minutes, creates stop. Redirects never depended on it. That is the right way round.

Challenge 2 of 8 · the permutation, as code

Four rounds, then walk back into range

N = 62 ** 7                       # 3.5 × 10¹² codes
def permute(i, key):
    while True:
        l, r = i >> 21, i & (2**21 - 1)  # 42 bits, two halves
        for k in range(4):
            l, r = r, l ^ (prf(key, k, r) & (2**21 - 1))
        i = (l << 21) | r
        if i < N: return base62(i, width=7)  # cycle walk
Why it worksEach round is invertible, so the whole is a bijection on 42 bits. Walking until the value falls below 62⁷ keeps it a bijection on the code space.

The first caller looks up; the rest wait

var group singleflight.Group
func resolve(code string) (Link, error) {
    if l, ok := local.Get(code); ok { return l, nil }
    v, err, _ := group.Do(code, func() (any, error) {
        l, err := sharedCache.Get(code)        // Redis, 2 ms timeout
        if err != nil { l, err = store.Get(code) } // PostgreSQL by PK
        if err == nil { local.SetWithTTL(code, l, 1, 60*time.Second) }
        return l, err
    })
    return v.(Link), err
}
