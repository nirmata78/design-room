Replaying recorded logs against a new build sounds like a batch job. It is only worth running if the same inputs give the same answer, and a release gate is only worth having if it can fail for the right reason. A compact reference solution at the Staff bar (L6/L7): theory, a three-version design, an alternate path, and six challenges. 63 minutes, 473 numbered slides.

The thesis: make every run a pure function of a pinned manifest, so outputs can be cached by content and differences mean something; then gate on paired statistics under a versioned policy.

IN THIS VIDEO
• Estimates: 250 TB and about 1,040 GPUs for an uncached 50,000-scenario gate, about $1 M a month of compute, 100 TB of cache
• Theory: six places randomness hides, five mechanisms (pinned manifests, simulated time, Merkle stage keys, paired intervals, quotas)
• Six challenges: the same build giving two answers, a perception change, release day, a log that does not react, block or pass, and a gate that cannot fail
