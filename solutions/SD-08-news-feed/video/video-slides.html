News feed · containersstage 4
Write path · two patterns, used together

Outbox decides what to publish; CDC carries it out

Transactional outbox

The event is a row in an outbox table, written in the same transaction as the post. Both commit, or neither.

CDC · change data capture

A connector tails the database's commit log and publishes each new outbox row to Kafka. No polling, no second write.

Either alone works small: outbox with a polling relay, or CDC on the posts table, which leaks its schema to every consumer.

def on_post_created(event):
    # authorTier was stamped into the event by the post service
    if event.author_tier == CELEB:
        # one write; readers merge this list at read time
        redis.lpush(f"celeb:{event.author_id}", event.post_id)
        redis.ltrim(f"celeb:{event.author_id}", 0, 99)
    else:
        push_to_followers(event)

    # only after every write succeeded: at-least-once
    kafka.commit(event.offset)
News feed · fan-out workerstage 4
Write path · code 2 of 2 · push to followers

A page of a thousand followers, one round trip

def push_to_followers(event):
    # MID authors reach only followers active today
    since = today() if event.author_tier == MID else today() - 30

    for page in graph.followers(event.author_id, page_size=1000):
        active = [f for f in page if last_seen(f) >= since]

        # all writes for the page in one round trip; keep newest 500
        with redis.pipeline() as p:
            for f in active:
                p.zadd(f"timeline:{f}", {event.member: event.ts})
                p.zremrangebyrank(f"timeline:{f}", 0, -501)
Re-delivered event? ZADD of an existing member is a no-op.

Read path · code 1 of 2 · gather candidates

Timeline, plus the celebrities this reader follows

def gather_candidates(user, cursor):
    ids = redis.zrevrange(f"timeline:{user}", 0, 499)
    if ids is None:
        ids = rebuild_by_pull(user)        # deep dive three

    # 5–20 lists, one round trip
    celebs = redis.smembers(f"celebsFollowed:{user}")
    ids += pipelined(redis.lrange(f"celeb:{a}", 0, 99) for a in celebs)

    # blocks and unfollows, enforced here
    hidden = redis.smembers(f"hide:{user}")
    ids = [i for i in unique(ids) if i.author not in hidden]
    return newest(ids, 200, older_than=cursor)
News feed · feed servicestage 4
Read path · code 2 of 2 · rank and hydrate

Rank inside a deadline; drop what was deleted

def feed(user, cursor):
    candidates = gather_candidates(user, cursor)
    # degrade, never fail
    try:
        ranked = ranking.score(user, candidates, deadline_ms=80)
    except Timeout:
        ranked = sorted_by_time(candidates)

    # hydration: 50 IDs → 50 posts, one multi-get
    top = ranked[:50]
    posts = redis.mget([f"post:{c.post_id}" for c in top])
    posts = [p for p in posts if p and not p.deleted]

    return posts, encode_cursor(top[-1])

News feed · celebritystage 6
Deep dive one · why the line is near 10 k–100 k followers

Fan-out lag grows with followers; pull cost grows with celebrities followed

Followers FPush: inserts and lag at 1 M/sPull: cost per reader open
2,0002 k inserts · 2 ms+1 list read (~0.3 ms pipelined)
10,00010 k · 10 mssame
100,000100 k · 100 ms, per postsame
10,000,00010 M · 10 s, and it bursts the workerssame
100,000,000100 M · 100 s per postsame: pull wins outright
Push cost scales with F; pull cost is flat per celebrity. The threshold is a config value, measured, not guessed.
