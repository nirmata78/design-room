The thesis
Never send a device a command; publish a desired state it converges to whenever it can. Release in waves that halt themselves, and give every device a last known good it returns to on its own.

Requirements · functional

Four things the system must do

FR1 · Know

Every device’s reported state and health, current when it last connected.

FR2 · Configure

Set desired configuration for a device or cohort; devices converge when they can.

FR3 · Release

Roll out signed firmware in waves, each soaked and compared before the next.

FR4 · Stop

Halt and revert a bad change automatically, including on devices that cannot boot it.

Theory · what it is

A control loop over devices you cannot reach

It is

Keeping a million unreachable, untrusted devices converging to a desired state, safely.

Not a message bus

A bus delivers to whoever is listening; most devices are not.

Not telemetry

Telemetry is the data plane; here health is only the signal for decisions.

Not app deployment

A server can be replaced; a device must survive its own bad update.

Theory · properties

Safety and liveness, stated separately

S1 · never bricked

No update leaves a device unable to boot a working image.

S2 · only signed, only its own

A device runs only signed images and accepts only its own desired state.

S3 · bounded harm

A bad release reaches at most its first wave.

L1 · converge

Every device that comes online converges to the latest desired state.

L2 · finish

A good release reaches the fleet in about two weeks.

Theory · mechanism M1

Desired and reported state, reconciled

Protects

L1.

How it works

Store a versioned desired document and the reported one per device; the device pulls and applies the latest; a loop nudges the drift.

Rules out

Commands lost to offline devices; replaying stale changes in order.

Costs

A device must be able to compute “apply this whole state”.

Technology · device gateway

MQTT over mutual TLS: one session per device, a certificate per device

How it is builtAbout 100,000 connections per node, 20 nodes. Each device presents its factory certificate; topics are scoped to its own ID.
OptionWhy it is chosen, or why not
EMQX cluster, MQTT 5, mTLSA small, battery-friendly protocol with persistent sessions and a device identity checked at the handshake.
HTTP pollingEvery device polls whether or not anything changed.
Kafka on devicesA server-side log, not a device protocol.

Two documents per device, each with a version

How it is builtOne row per device: desired and reported JSON with versions. Writers use WHERE desired_v = $read.
OptionWhy it is chosen, or why not
PostgreSQL, one row per device1 M rows of a few kilobytes is small; conditional updates on a version make every desired-state change a compare-and-set.

Technology · firmware delivery

Signed images, fetched by range, verified on the device

How it is builtThe desired document names the URL, size, SHA-256 and an offline signature. The agent fetches by range, resumes, and verifies before writing.
OptionWhy it is chosen, or why not
Object storage + CDN; images signed offline50 TB per release must not cross the gateway; a device-side signature check defeats a compromised CDN.
Images through the brokers50 TB crowds out every control message.
Trusting TLS to the CDNTLS proves the server, not the image.

Challenge 1 of 6 · the second fix

A kill switch below the agent

Confirm means “can be updated”

The watchdog confirmation includes a round trip: fetch desired, report it. A deaf agent never confirms.

A separate, signed path

A tiny recovery client in the bootloader polls one signed URL daily: “revert to slot A”.

Honest limit

A bug that passes both checks and only fails later needs the next release; waves keep it small.

“I'd never rely on a server to rescue a device. New configs and images are pending until the agent confirms, after a full round trip to us, within a watchdog deadline. Three failed boots and the bootloader returns to the last known good on its own; a signed recovery path sits below the agent.”
