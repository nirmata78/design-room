Requirements · minutes 3–8

Two answers that fix the core

"Can we ever oversell?"

Never. One place where each seat's state lives, changed atomically.

"Pick a seat, or best available?"

Pick from a map. Contention is per seat, not on one counter.

Checkout: ~3 minutes

You can't hold a transaction open that long. The reservation is data: a hold with an expiry.

Payment: 2–10 s, can time out

"Didn't answer" is not "declined". Seats must not be released while the outcome is unknown.

Fairness is a product decision

First-come is expected; a queue or a lottery is fine if argued. The promoter owns it.

A couple of seconds. So the seat map can be a cached snapshot.

PostgreSQL for the seats

OptionVerdictWhy
PostgreSQL, sync replicachosenmulti-row all-or-nothing claim with row locks; CHECK and UNIQUE in the DB; RPO 0 on failover
Redis + Luarejectedasync replication: a hold acked, primary dies, replica promoted, seat free again = oversell
DynamoDB / Cassandrarejectedmulti-item conditional writes are limited or costly; LWT is slow under contention; no relational guard
Spanner / CockroachDBnot neededglobal serializability we don't need: one event lives in one region; 500 writes/s fit one primary

Technology · waiting room · selected against the alternatives

Redis for the queue

OptionVerdictWhy
Redis Cluster + Luachosen50k trivial ops/s at T0; single-threaded, so INCR and Lua are atomic; hash tags keep an event on one node
PostgreSQL rowsrejected50,000 INSERTs a second for data that may lose a second: wrong cost for the durability
Kafka as the queuerejectedwe ask "what's my position?" and "advance by 33", not "consume next"
In-process memoryrejectedno shared pointer across nodes; a restart loses the line
What Redis can lose (≈1 s with AOF everysec) is survivable: the seq lives in the fan's signed token.

Deep dive 1 · the claim, in one transaction

The WHERE clause is the availability check

BEGIN;
SELECT seat_id FROM event_seat WHERE event_id = :e AND seat_id = ANY(:seats)
 ORDER BY seat_id FOR UPDATE NOWAIT;               -- sorted: no deadlock cycle; NOWAIT: fail fast
UPDATE event_seat SET state = 'HELD', hold_id = :h, version = version + 1,
       hold_expires_at = now() + interval '5 minutes'
 WHERE event_id = :e AND seat_id = ANY(:seats)
   AND (state = 'AVAILABLE' OR (state = 'HELD' AND hold_expires_at < now()))  -- lazy expiry
RETURNING seat_id;                                 -- fewer rows than asked → ROLLBACK → 409
INSERT INTO hold   (hold_id, event_id, user_id, seat_ids, status, expires_at, idem_key) …;
INSERT INTO outbox (event_id, event_type, payload) VALUES (:e, 'SeatsHeld', …);
COMMIT;

AlternativeWhat goes wrong
Distributed lock, Redis SETNX per seata second system's failure modes; a lease can expire mid-transaction
SERIALIZABLE isolationcorrect, but under contention it aborts many transactions; retries for nothing

Deep dive 2 · the join, atomic in one Lua script

A join racing the T0 flip lands cleanly on one side

-- join.lua   KEYS: phase:{e} lobby:{e} next:{e} seqOf:{e}   ARGV: userId, secretScore
if redis.call('GET', KEYS[1]) == 'LOBBY' then
  redis.call('ZADD', KEYS[2], 'NX', ARGV[2], ARGV[1])  -- NX: re-joining keeps the first draw
  return {'LOBBY', 0}
end
if redis.call('ZSCORE', KEYS[2], ARGV[1]) then return {'LOBBY', 0} end   -- ask /queue/me
local s = redis.call('HGET', KEYS[4], ARGV[1])
if s then return {'QUEUE', tonumber(s)} end              -- idempotent re-join after T0
local seq = redis.call('INCR', KEYS[3])                  -- late arrivals: plain FIFO
redis.call('HSET', KEYS[4], ARGV[1], seq); return {'QUEUE', seq}
At T0, a million /queue/me calls over 20 s of client jitter: 50k ZRANK/s, O(log n) ≈ 20 steps each.

Ticket booking · expirydeep dive 4
Deep dive 4 · the sweeper

SKIP LOCKED for "any", NOWAIT for "these"

WITH expired AS (
  SELECT event_id, seat_id FROM event_seat
   WHERE event_id = :e AND state = 'HELD' AND hold_expires_at < now()
   ORDER BY hold_expires_at LIMIT 500
   FOR UPDATE SKIP LOCKED                  -- skip rows a buyer is claiming right now
)
UPDATE event_seat s SET state = 'AVAILABLE', hold_id = NULL, hold_expires_at = NULL,
       version = s.version + 1
  FROM expired x WHERE s.event_id = x.event_id AND s.seat_id = x.seat_id
RETURNING s.seat_id;                       -- + outbox 'SeatsReleased', same commit
Every 5 s, 500 a batch: up to 100 releases a second, short locks, parallel-safe. PAYMENT_PENDING is never touched.
