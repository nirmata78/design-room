# Part 4 · diagram specifications

Eight new figures, two sessions (four each). `p2-pause` is reused from part 2 and is not redrawn.
Rules: `diagrams/README.md`.

## p4-chubby-session
- **Kind:** timeline, canvas 1600 × 760. Time axis 0 s to 70 s, ticks at 0, 12, 24, 36, 48, 60.
- Lane `Master`: bars "lease 12 s" from 0 to 12 and 12 to 24 (blue), each starting at a small
  "KeepAlive reply" arrow down to the client lane. At 24 s a red cross "master fails"; a grey bar
  "no master" from 24 to 40; at 40 a green box "new master · extends every session".
- Lane `Client`: matching bars "local lease (shorter)" ending about 1 s before each master bar
  (light blue). From 23 s an amber bar "jeopardy · cache emptied · calls wait" running to 41 s, with
  a bracket above it "grace period 45 s" spanning 23 s to 68 s (dashed).
- At 41 s a green event on the client lane "safe · session saved". Beside the bracket's end at 68 s,
  in red: "no master by here → session expired · every lock lost" (**highlight**).

## p4-election-epoch
- **Kind:** Seq, canvas 1600 × 820. Participants `Node A`, `Node B`, `Coordination store`,
  `Worker`.
- 1. A → Store: "create /leader if absent · lease 10 s". 2. Store → A: "ok · create_revision **812**".
  3. B → Store: "create /leader if absent". 4. Store → B: "exists · watch it". 5. A → Worker:
  "assign task · epoch 812". 6. note over A: "paused…" 7. Store → B: "key deleted (lease expired)".
  8. B → Store: "create /leader" → reply "ok · **901**" (one arrow each way). 9. B → Worker: "assign
  · epoch 901". 10. A → Worker: "assign · epoch 812" (**highlight**, red) with Worker note
  "812 < 901 → refused".

## p4-herd
- **Kind:** two panels side by side, canvas 1600 × 720, titles "Everyone watches the lock" and
  "Each watches its predecessor".
- **Left:** a `lock` box at top; 8 small waiter circles below (label "… 1,000 waiters"), each with a
  red arrow up to the lock. Caption: "one release → 1,000 wake, 1 wins, 999 retry".
- **Right:** a horizontal chain of keys `/q/812 (holder)`, `/q/813`, `/q/814`, `/q/815` …; from each
  key a green arrow back to the one before it, labelled "watch". Caption: "one release → **one**
  wake-up".
- Bottom line across both: "over 1,000 releases: about 500,000 wasted attempts vs 0".

## p4-redlock-clock
- **Kind:** timeline, canvas 1600 × 780. Five lanes `Node 1` … `Node 5`.
- At t = 0, `Client 1` writes the key on nodes 1, 2, 3 (three blue bars "held by C1 · expiry 10 s").
- On node 3, at t = 3 a red lightning icon "clock jumps forward 8 s"; node 3's bar ends at t = 3
  ("expired early").
- At t = 4, `Client 2` writes on nodes 3, 4, 5 (three amber bars "held by C2").
- A red bracket from t = 4 to t = 10 across all lanes (**highlight**): "two clients each hold a
  majority".
- Caption: "the same overlap happens without a jump if C1 pauses past its expiry · no token to
  reject the late one".

## p4-stale-discovery
- **Kind:** Seq, canvas 1600 × 720. Participants `Client`, `Registry`, `10.0.0.7 (old: shard 7)`,
  `10.0.0.7 (new: shard 12)` — draw the last two as one lifeline that changes colour at step 2.
- 1. Client → Registry: "who owns shard 7?". 2. Registry → Client: "10.0.0.7" (client note:
  "cached"). 3. note on the server lifeline: "server dies · address reused for shard 12".
  4. note on Registry: "updated in ~10 s". 5. Client → 10.0.0.7: "write to shard 7" (**highlight**,
  red). 6. note: "accepted by the wrong server".

## p4-registry
- **Kind:** block diagram, canvas 1600 × 760.
- Three server boxes on the left `server a`, `server b`, `server c`; each with an arrow right to a
  central `Coordination store` box labelled "register under lease · renew".
- Inside the store: a small key list "/members/a · /members/b · /members/c · revision 950".
- Right: two client boxes with arrows from the store labelled "read at 950 · watch from 951".
- A green arrow from a client back to `server b` labelled "request · shard 7 · epoch 901"; at server
  b a small check box (**highlight**): "is shard 7 mine at epoch 901? else refuse".

## p4-config-push
- **Kind:** block diagram, canvas 1600 × 640.
- Left to right: `Engineer` → `Config source (reviewed)` → `Config service · v42` → a fan of many
  small server boxes (12, in a grid) all turning red.
- Arrow from service to fan labelled "push · seconds" (**highlight**, red).
- Under it, two bars for comparison: "binary deploy: staged over hours" (green, long) and "config
  change: everywhere in a minute" (red, short).

## p4-config-flow
- **Kind:** block diagram, canvas 1600 × 820, six numbered steps.
- `Config service` box at left holding "snapshot v40 · deltas 40→41→42".
- Arrows to a `Server` box: ① "new version" (the service itself), ② "stream: delta 41→42",
  ③ "poll every few min: I have v41" (dashed, labelled "backstop"), ④ inside the server
  "verify checksum", ⑤ a rollout strip across the top "canary → one zone → all, health check between
  each", ⑥ inside the server "fails? keep last known good (on disk)" (**highlight**).
- Server also has an arrow back "report: applied v42 · hash 9c1e…".
