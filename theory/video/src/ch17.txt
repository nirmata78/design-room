## 17.1 The front door

= dia | The front door | What is inside: packets, then requests
p11-l4-l7
N: The front door in one picture, from part eleven. A layer four balancer places connections, fast and blind to the protocol. A layer seven proxy terminates them and places each request, and can route, retry and limit. Behind them sits everything else. The four cards in this group are the four layers a request crosses before it reaches your code.

## 17.2 Databases and stores

= dia | Databases and stores | What is inside: a log, a memory table, sorted files
p7-lsm-write
N: Inside most stores, from part seven: a write-ahead log for durability, an in-memory sorted table, and immutable sorted files merged in the background. A B-tree engine updates pages in place instead. Around that engine, each store in this group adds a different answer to replication, partitioning and transactions, and that answer is what decides when to draw it.

= cards | BLK-06 · Block | Relational database · Cloud SQL, AlloyDB ↔ PostgreSQL, MySQL

N: The relational database. Draw it for transactions, joins and constraints, up to tens of thousands of writes a second and a few terabytes per primary, which covers more systems than people expect. Not for unbounded write scale-out on one primary. Open it up with B-trees and indexes in part seven, isolation and locks in part eight, and failover in part five.

## 17.6 Three facts worth having exact

= list | Three facts | Easy to get wrong, checked November 2026
- **Pub/Sub**: ack deadline 10 s by default, at most 600 s; retention 7 days by default, at most 31; dead-lettering after 5 to 100 attempts; ordering keys give order within a region
- **Kafka** removed ZooKeeper in version 4.0, March 2025: its controller quorum now runs on Raft
- **Colossus** keeps file-system metadata in Bigtable behind a metadata service; data flows directly between clients and file servers; separate services rebalance and reconstruct
N: Three facts worth having exact, checked in November twenty twenty-six. Pub Sub's acknowledgement deadline is ten seconds by default and at most six hundred, retention seven days by default and at most thirty-one, and dead-lettering after five to one hundred attempts, with ordering keys giving order within a region. Kafka removed ZooKeeper in version four point oh, in March twenty twenty-five, and its controllers now agree through Raft. And Colossus keeps its file-system metadata in Bigtable behind a metadata service, while data flows directly between clients and file servers.

= table | Assembly · a cache tier | Which blocks, what each owns, the managed replacement

## 17.9 Probe drills

= probe | Why a wide-column store and not a relational database here?
- The **write rate** exceeds one primary, and access is by **row-key range**
- No multi-row transactions or ad hoc joins are needed
- If they were, distributed SQL, at a latency price
C: Because the write rate is beyond what one relational primary can take, and every query is a scan by row-key range, which the wide-column store serves directly from its sorted tablets. We do not need multi-row transactions or ad hoc joins. If we did, I would choose distributed SQL instead, and pay a consensus round trip per write.

= probe | Why a log and not a queue?
- **Several consumers** need the same events, and replay after a bug
- **Order per key** matters
- Tasks of varying cost done once each would favour a queue
C: Because several consumers need the same events independently, and we must be able to replay a week after a bug, which a queue cannot do once messages are acknowledged. And we need order per key. If the messages were tasks of varying cost, each done once, with redelivery and dead letters, I would choose a queue.

= probe | Why a coordination service and not the cache for this lock?
- It is a **correctness** lock: overlap corrupts data
- Needs consensus and a **fencing token** the resource checks
- A cache lock is fine only for **efficiency**
C: Because this lock protects correctness: two holders would corrupt the ledger file. That needs a consensus-backed lock that survives a node failure and issues a fencing token, which the storage checks on every write. A lock in a cache is fine when two holders only means repeated work, which is not the case here.

= probe | "Do not use the managed product. Build it." Which part do you open?
- Name the **mechanisms** the product provides, then the part for each
- A cache: parts 6 and 9; a scheduler: 3, 4 and 15; a blob store: 5, 6 and 7
- Build the differentiating mechanism in depth; keep the rest as boxes
C: I would name the mechanisms the product provides and open the part for each. For a cache, partitioning and caching, parts six and nine. For a scheduler, consensus, coordination and part fifteen. For a blob store, replication, partitioning and storage, parts five to seven. And I would go deep on the mechanism the question is really about, keeping the rest as clearly labelled boxes.
