Five sentences that pass this round
  1. This is a read-heavy key-value lookup. A hundred reads per write and 350,000 redirects a second at peak, so the design is mostly about making reads cheap.
  2. Seven base62 characters give 3.5 trillion codes, about twenty times what five years at 100 million links a day needs.
  3. Codes come from leased counter ranges passed through a keyed permutation. They're unique without collision checks and unguessable without a central bottleneck.
  4. Redirects return 302 with short cache lifetimes, because analytics, expiry and takedowns all need clicks to keep reaching us.
  5. Analytics leave through an asynchronous stream. Nothing on that path can slow down or fail a redirect.

Why redirects get more nines than creates: a broken redirect breaks every link ever printed, emailed or encoded in a QR code; a failed create is one user retrying. Different targets justify separate services (§5).

What "p99 < 50 ms" means

99 out of 100 requests finish within 50 ms. Averages hide the slow tail, and at 115,000 redirects a second the slowest 1% is still 1,150 users every second. "Server side" means from the request reaching our edge to the response leaving it; the user's own network round trip isn't ours to promise.

Say it

"The redirect is the product, so it gets four nines and a 50 ms p99, and it must keep working when link creation is degraded. Once a code is issued it must always resolve to the same URL, never lost and never reused, and codes shouldn't be guessable, because people shorten links to private documents."

Caching headers on the redirect

private, max-age=60 lets the browser reuse the redirect for a minute but tells shared caches not to store it. CDN-Cache-Control (RFC 9213) gives our own CDN a separate lifetime that overrides Cache-Control for the edge. If your CDN doesn't support it, use public, max-age=60, s-maxage=60 or set the TTL in CDN config. Either way, deleting or disabling a link takes effect within about a minute.

Idempotency keys and cursors

Idempotency key: the client generates a UUID per user action and resends it on retry. The server stores (owner, key) → response for 24 hours with a conditional insert; a duplicate gets the stored response, not a second link. Cursor pagination: the cursor is an opaque encoding of the last (created_at, code) seen. Unlike OFFSET, it costs the same on page 1,000 and doesn't skip or repeat rows when new links arrive.

Interviewer probes

Why isn't the redirect versioned? Short links are printed and shared forever, so the URL format is a permanent contract. Only the management API is versioned.

Why 302 and not 301? Analytics, expiry and deletion are requirements, and a cached 301 bypasses all three. If the business later valued cost over analytics, switching is a one-line change.

DynamoDB facts worth knowing
  • Items up to 400 KB. A partition holds ~10 GB and serves up to 3,000 reads and 1,000 writes per second (capacity units); adaptive capacity splits hot partitions, but one key can't exceed one partition's limit.
  • Global secondary indexes are eventually consistent: "my links" may lag a new link by a moment.
  • TTL deletion is lazy, typically within days, not seconds, so expiry is checked on read.
  • Global tables replicate asynchronously between regions, last writer wins.

The hot-partition trap

Sequential codes in a range-partitioned table send every new link, which is also the most-clicked one, to the last partition. Hash partitioning on a randomized code avoids it.

Interviewer probes

Why not just Postgres? It works, and at small scale I'd start there. At 90 TB I'd be building sharding, routing, resharding and per-shard failover myself, for a workload that uses nothing relational. The ad hoc queries I'd miss belong in the analytics store anyway.

How is the table partitioned? By a hash of the short code. Codes are uniformly random (§6), so load spreads evenly.

5High-level designSTAGE 4 · MIN 15–25

Write path: POST /v1/links

  1. Authenticate and rate-limit by API key and IP.
  2. Validate and normalize the URL (box below), and check it against a local blocklist.
  3. Take the next ID from this instance's leased block; permute and encode it into a 7-character code (§6).
  4. Conditional put into the key-value store.
  5. Write the mapping to Redis too: new links are usually clicked within seconds.
  6. Return 201. The deep safety scan runs asynchronously and can disable the link later.

Read path: GET /{code}

  1. CDN: popular links are answered at the edge.
  2. In-process LRU in the redirect instance: microseconds.
  3. Redis: the broad hot set, sub-millisecond.
  4. Key-value store only on a miss; populate Redis on the way back.
  5. Check status and expiry, return 302, 404 or 410.
  6. Emit a click event to Kafka without waiting.
URL validation and normalization
  • Only http and https: reject javascript:, data:, file:.
  • Max ~2,048 characters; must parse as a URL with a host.
  • Lowercase scheme and host, drop default ports, convert international domains to punycode.
  • Don't touch path or query semantics: /A and /a can be different pages.
  • Reject our own short domain as a destination, which prevents redirect loops and link laundering.
Why stateless services matter

Neither service keeps anything it can't lose: the ID block and the LRU are caches of state that lives elsewhere. So any instance can serve any request, autoscaling is just adding pods, and a crash costs at most one unused ID block. At ~10k requests per second per redirect pod, origin peak (~210k/s after the CDN) needs a few dozen pods.

Interviewer probes

Why split the link service and the redirect service? They scale on different curves (100×), have different targets (four nines vs three), and have different dependencies. The redirect service must not depend on the ID allocator, auth or the scanner. If those fail, creation degrades and every existing link keeps working. Separation makes that isolation structural instead of hopeful.

Say it

"Writes are small and must be unique; reads are huge and must be fast; events are the biggest volume and can be late. So: a small write service with a conditional insert, a stateless read service behind three cache layers, and an asynchronous stream for clicks."

The birthday problem, for random codes

With n codes taken out of N, a new random code collides with probability n/N, about 5% by year five. But the first collision arrives after only about √(πN/2) ≈ 2.35 million codes, within the first hour at our rate. So random codes need a conditional insert from day one.

static final String ALPHA = "0123456789"
    + "abcdefghijklmnopqrstuvwxyz"
    + "ABCDEFGHIJKLMNOPQRSTUVWXYZ";
// 62^7 codes; 4 secret round keys
static final long SPACE  = 3_521_614_606_208L;
static final long MASK21 = (1L << 21) - 1;
static final long[] KEYS = loadKeysFromVault();

// round function: splitmix64 finalizer
static long mix(long z) {
  z = (z ^ (z >>> 30)) * 0xBF58476D1CE4E5B9L;
  z = (z ^ (z >>> 27)) * 0x94D049BB133111EBL;
  return z ^ (z >>> 31);
}
// a bijection on [0, 2^42)
static long permute(long x) {
  long l = x >>> 21, r = x & MASK21;
  for (long k : KEYS) {
    long t = l ^ (mix(r ^ k) & MASK21);
    l = r; r = t;
  }
  return (l << 21) | r;
}
static String toCode(long id) {  // id < SPACE
  long y = permute(id);
  while (y >= SPACE) y = permute(y); // cycle walk
  char[] c = new char[7];
  for (int i = 6; i >= 0; i--) {
    c[i] = ALPHA.charAt((int) (y % 62)); y /= 62;
  }
  return new String(c);
}
How a Feistel network works

Split the 42-bit number into two 21-bit halves, L and R. Each round sets L, R = R, L xor F(R, key). Any function F works, because each round can be undone: knowing the new L (old R) you recompute F and xor it away. So the whole thing is a bijection: different IDs always give different outputs, and it's reversible with the keys.

Cycle walking: the permutation covers 2⁴² values but codes must stay below 62⁷, which is 80% of that. If the output is too big, permute it again; on average 1.25 passes. The result is still a bijection on [0, 62⁷).

Round function: splitmix stops casual enumeration. For real secrecy, use AES-based FF1 format-preserving encryption (NIST SP 800-38G) or HMAC-SHA-256 as F.

Interviewer probes

Do you still need the conditional write? Yes: as a safety net, and because a custom alias might equal a code the generator produces later. On a clash the service skips to the next ID. To make it near-impossible, aliases must be ≥ 8 characters or contain a hyphen, which isn't in the generated alphabet. Plus a reserved-word list (api, admin, login…) and an offensive-terms filter.

Same long URL submitted twice? Separate codes by default: two owners need separate analytics and separate deletion. For per-user deduplication, add an index on (owner_id, hash(normalized URL)). Retries are covered by the idempotency key.

The allocator is down. Instances keep issuing from the blocks they hold, minutes of headroom at peak. Only then does creation stop; redirects never notice.

Why not Snowflake? 64 bits is 11 base62 characters, and the embedded timestamp leaks creation time. We need only ~42 bits.

Three layers, three jobs

  • CDN absorbs viral links: a million clicks a minute cost one origin request per edge per minute. Counts come from CDN logs.
  • In-process LRU (Caffeine), top ~100k links: shields Redis from hot keys.
  • Redis, cache-aside with LFU eviction: the ~60 GB hot set. For links, popularity predicts the next click better than recency.
Cache-stampede protection (single-flight)

When a hot key expires, thousands of requests miss at once. Coalesce them so one does the load and the rest wait for its result:

// Caffeine coalesces concurrent loads per key
AsyncLoadingCache<String, Link> local =
  Caffeine.newBuilder()
    .maximumSize(100_000)
    .expireAfterWrite(Duration.ofSeconds(30))
    .buildAsync((code, ex) -> supplyAsync(
        () -> redisThenStore(code), ex));
// 10,000 concurrent get("fN7J2J9")
//   → one redisThenStore() call

Also add TTL jitter (±10%) so keys written together don't expire together.

Bloom filter math, and why it's optional

Bits needed: m = −n·ln p / (ln 2)². For n = 180 billion codes and p = 1%, that's ~1.75 × 10¹² bits ≈ 219 GB, with k = 7 hash functions. Far too big for every pod, so the first defenses against scanning are negative caching and 404 rate limits.

Interviewer probes

Someone scans random codes. Cache a "not found" marker for a few minutes, so repeated misses don't reach the store; rate-limit clients with many 404s, which is the signature of enumeration. A Bloom filter only if it becomes a real problem.

How do expiry and deletion interact with three caches? Expiry: the timestamp travels with the cached value and is checked on every hit, so links die on time whatever the TTL. Deletion: delete the record, delete the Redis key, broadcast an invalidation so pods drop it from their LRU, and purge the CDN, which is mandatory for malicious-link takedowns.

A single link gets millions of clicks per second. The CDN takes nearly all of it. If it couldn't, every pod's LRU would, since one code and its URL fit in every instance's memory.

CAP and PACELC, applied

CAP: during a network partition you choose consistency or availability, per operation. Redirects choose availability: serve a possibly stale mapping, since a mapping never changes once issued. Creation chooses consistency: if uniqueness can't be guaranteed (no lease, no conditional write), refuse with 503.

PACELC: "else" (no partition) you trade latency against consistency. A synchronous cross-region write would cost 70–90 ms per create, so replication between regions is asynchronous, and we accept a tiny loss window.

Interviewer probes

Two regions could hand out the same code. Not with region slices: EU leases only from [0, 1.17 T), US only from [1.17 T, 2.35 T).

A link created in Europe is clicked in the US 300 ms later. It may not have replicated yet. On a miss, decode the code → ID → home region, and read from there. A rare, slower path that gives read-your-writes across regions.

A whole region goes down. GeoDNS health checks move traffic (RTO ≈ DNS TTL + detection, keep TTLs at 30–60 s). Redirects keep working because every link is replicated. Loss (RPO): links created in the last ~second before the failure, which hadn't replicated. That's the price of not paying 70–90 ms on every create.

  • Producer: asynchronous, batched, bounded buffer. When Kafka is slow, drop events rather than block. Losing clicks in an incident is acceptable; failing redirects isn't.
  • Partition by code, so one link's events stay ordered and land on one Flink task.
  • One-minute tumbling windows on event time, with watermarks and ~2 minutes of allowed lateness for stragglers.
  • Delivery: Kafka is at-least-once; Flink checkpoints give exactly-once state; ClickHouse keeps aggregates in a ReplacingMergeTree keyed by (code, minute, dims), so a replayed window replaces its row instead of double counting.
Why not increment a counter on the link row?

A viral link would turn its row into a write hot spot: hundreds of thousands of increments a second on one key, beyond any partition's 1,000 writes/s, competing with redirect reads on the same table. Aggregating first turns a million events into one write per minute.

Unique visitors: HyperLogLog

Exact distinct counts need memory proportional to the visitors. A HyperLogLog sketch estimates them in ~12 KB with ~0.8% error, and sketches merge: hourly sketches combine into daily or monthly uniques without rescanning. ClickHouse (uniqHLL12, uniqCombined) and Redis (PFADD/PFCOUNT) both have them.

Bots and privacy

Filter known crawler user agents, link-preview fetchers (Slack, LinkedIn, iMessage) and datacenter IP ranges, and flag inhuman click rates. Keep raw events 90 days, derive country then drop the IP, and support per-user deletion.

Say it

"Analytics never slows a redirect. Events go to an asynchronous producer that drops rather than blocks, Kafka keyed by code, Flink one-minute windows, ClickHouse for the stats API. Uniques via HyperLogLog. And no counters on the links table: a viral link would melt its partition."

Never reuse a code

Old short links live on in emails, documents and printed QR codes. If an expired code later pointed somewhere else, we'd send those people to a stranger's, possibly malicious, destination. With 3.5 trillion codes there's no shortage, so reuse buys nothing. Expired links return 410 Gone; the code stays retired forever.

Expiry mechanics and enumeration

Expiry: checked on every read (cheap, exact); the database TTL attribute deletes the item in the background, days later. Enumeration: the keyed permutation makes codes non-sequential, and 404 rate limits slow scanners. Tell users plainly that a short link isn't access control: private documents need their own authentication.

The failure people forget

A bad deploy of the redirect service breaks every link ever issued, at once. It's the highest-impact failure in the system, and the mitigation is process, not architecture: canaries, small blast radius, fast automated rollback.

What to monitor

Redirect success rate and p99 per region; cache hit ratio per layer; 404 and 410 rates (scanning, bad deploys); create error rate; allocator lease latency; Kafka producer drop rate and consumer lag; disabled-link count (abuse waves).

12Rapid-fire follow-upsMIN 52–57

Cover the answer, say yours out loud, compare. One or two sentences each.

What consistency model do you use?
Strong where it matters: code uniqueness, via leases and conditional writes. Eventual everywhere else, with the cache write on create covering read-after-create.
Could the codes be shorter?
Start at six characters and move to seven when the space runs out, about 1.6 years in. Old codes keep working: the redirect just looks up whatever string it gets.
How do you stop enumeration?
Keyed permutation, 404 rate limits, and honesty that short links aren't access control.
A user asks to delete all their data.
Delete their links and invalidate all three cache layers; codes stay retired. Raw click events are deleted or anonymized; aggregates hold no personal data.
How would you support editing the destination?
With 302 it's an update plus the same invalidation as deletion. Keep a history for audit and re-run the safety scan: "harmless, then phishing" is a known trick.
Custom domains per customer (brand.co/sale)?
Make the key (domain, code); codes are unique per domain. Route by Host header; TLS certificates via ACME automation.
Why not cache the redirect forever with 301?
Then we can't count clicks, expire, delete or take down a malicious link for anyone who clicked once.
How do you load-test this?
Replay a skewed (Zipf) click distribution at 2× peak, then kill Redis mid-test: the store must survive the cache loss.
What's the first bottleneck at 10× traffic?
Hot keys. The CDN and pod LRUs absorb them; the store and Redis scale horizontally for the rest.
Why not Kafka or a queue for creating links?
Creation must answer synchronously with the code, and the write rate (3.5k/s) is easy for the store. A queue adds latency and nothing else.
What would you build first?
One region: both services, Redis, DynamoDB, leased IDs, 302s, rate limits and the blocklist (abuse arrives on day one). Then analytics, then CDN caching, then multi-region.
