Five sentences that show you own Redis
  1. Redis executes commands on one thread, so every command (and every Lua script) is atomic without locks. It's fast because the data is in RAM and most commands are O(1) or O(log n).
  2. Replication is asynchronous, so a failover can lose a write the client was told succeeded. That's fine for the queue and fatal for seats, so seats live in PostgreSQL.
  3. In Cluster mode a key's slot is CRC16(hash tag) mod 16,384. I tag every key with {event_id}, so one event's keys share a node and one script can touch them all.
  4. The waiting room is a sorted set with a secret random score, a counter for late arrivals and one pointer that only grows. Every operation is O(log n) or better.
  5. Redis locks are for efficiency, not correctness. Correctness comes from a fencing check in the system of record: here, the conditional UPDATE and UNIQUE(event, seat).

1Redis in one page

Redis is an in-memory data-structure server. Keys map to typed values (strings, hashes, lists, sets, sorted sets, streams, bitmaps and more), and each type comes with server-side operations. You send "add this member with this score" instead of reading a value, changing it and writing it back. One thread executes the commands. Persistence to disk is optional, replication is asynchronous, and Redis Cluster scales it out by splitting the key space into hash slots.

Good atNot good at
Sub-millisecond reads and writes on small, hot stateBeing the system of record for money or inventory (async replication, no consensus)
Atomic counters, sets, rankings and bitmaps with no read-modify-write racesLarge values or unbounded collections (one slow command stalls the node)
Short-lived state with TTLs: holds, leases, rate limits, idempotency keysAd-hoc queries, joins, secondary indexes (Redis 8's query engine helps, but it's not SQL)
Fan-out of small messages; caching anything expensive to computeDatasets much larger than RAM (cost grows with memory)

The three Redis roles in the design

  • Queue state (the waiting room): the lobby sorted set, the sequence counter, the admission pointer, the sold-out flag, admission markers and the controller's lease.
  • Map snapshots: versioned 6.25 KB availability bitmaps written once a second by the snapshot builder and read ~5,000 times a second.
  • Edge state: rate-limit buckets and the JWT deny-list, read by the gateway.

Why they're separate deployments

They differ in eviction policy (queue state must never be evicted; map snapshots can be rebuilt), blast radius (a cache stampede mustn't slow joins at T0) and scaling (the queue store scales with waiting fans, the map store with shoppers). One shared Redis would force one policy on all three.

Say it

"I use Redis for three things: the waiting-room state, the seat-map snapshots and edge state like rate limits. None of them is the source of truth for a seat. That's PostgreSQL, so losing a second of Redis writes costs a pause in the line, never a double sale."

2Why it's fast: the execution model

  • Event loop. One thread multiplexes thousands of sockets with epoll/kqueue. It reads a command, runs it to completion and queues the reply. The data path has no locks and no context switches.
  • I/O threads (6.0+, reworked in 8.0). Reading and parsing requests and writing replies can be spread over io-threads. Execution stays on the main thread, so atomicity is unchanged; throughput rises when the network is the bottleneck.
  • Background threads handle AOF fsync, lazy freeing (UNLINK, lazyfree-*) and closing files. A forked child writes RDB snapshots and AOF rewrites, sharing memory copy-on-write.
  • Numbers to quote: a few microseconds of CPU per simple command; ~100k–200k ops/s per node without pipelining (bound by syscalls and the network, not execution) and 1M+ with it. A same-zone round trip (~0.2–0.5 ms) costs far more than the command itself.
Why single-threaded is a feature

Atomic by construction. INCR needs no compare-and-swap, ZADD NX can't race, and a Lua script is a critical section for free. The cost is that latency is shared: one slow command stalls every client of that node. That's why the rule is keep every command and script O(1) or O(log n).

What blocks the loop

KEYS *; SMEMBERS, HGETALL or LRANGE 0 -1 on huge collections; DEL of a million-element key (use UNLINK); long Lua scripts; huge MULTI blocks; fork() of a very large dataset (page-table copy; disable transparent huge pages). Each is O(N) on the only thread.

Say it

"Redis is fast because the data is in memory, the commands are O(1) or O(log n), and one thread runs them, so there's no locking. The same property makes every command atomic, which is why I can do the join and the phase check in one script without a distributed lock."

Why a sorted set for the lottery

ZADD NX with a secret random score inserts each fan into a uniformly random order in O(log n), with nothing to do at T0. ZRANK gives the position in O(log n), ZCARD the size in O(1). Shuffling a million entries at T0 would be O(n) work in the worst second. NX keeps the first draw, so re-joining can't re-roll it.

The bit-order trap

Java's BitSet.toByteArray() puts bit 0 in the least significant bit of byte 0; Redis's SETBIT/GETBIT/BITPOS use the most significant. SD-47's builder ships BitSet bytes and the client decodes them, which is consistent. Mix in GETBIT on the same key and you read the wrong seat.

5Expiry and eviction

Expiry

  • A TTL is stored as an absolute Unix time in milliseconds in a separate expires dictionary.
  • Passive: any access checks the TTL first, so an expired key is never returned.
  • Active: about 10 times a second a time-boxed cycle samples keys that have a TTL and deletes the expired ones, repeating while many in the sample were expired. Expired keys can linger in memory briefly but are invisible.
  • Replicas don't expire keys themselves. The primary sends a DEL. A replica returns nil for a logically expired key.
  • The keyspace notification expired fires when the key is actually deleted, which can be later than the TTL.

Eviction policies (maxmemory-policy)

LRU and LFU are approximated by sampling maxmemory-samples (default 5) keys, not by an exact global list.

Two expiry traps in ticketing

Don't drive hold expiry from keyspace notifications. They fire late, Pub/Sub delivery is at-most-once, and a disconnected listener misses them. Use the DB predicate (SD-47) or a sorted-set due queue (§10.7). Jitter TTLs: 50,000 keys written at T0 with the same TTL expire in the same second.

Say it

"The queue store runs noeviction with its own memory budget; caches run allkeys-lfu on a separate deployment. I never let an LRU decide to drop someone's place in line."

EVAL vs Functions

EVAL sends the script text; EVALSHA sends its SHA1 and fails with NOSCRIPT after a restart or failover, so clients resend the text (Spring Data Redis does this for you). Functions (7.0) are named libraries stored in the dataset, persisted and replicated with it, like stored procedures. Scripts are replicated as their effects (the writes), so calling TIME inside a script is safe.

Script and transaction traps

Declare every key in KEYS: in Cluster, a key built inside the script bypasses routing and can fail with CROSSSLOT. Keep scripts short: after busy-reply-threshold (5 s) other clients get BUSY, and SCRIPT KILL works only if nothing has been written yet. MULTI doesn't roll back: a WRONGTYPE in command 2 of 3 still commits 1 and 3.

Persistence ≠ replication

The AOF protects this node against a restart. It does nothing for a failover: if the primary dies and a replica is promoted, whatever the replica hadn't received is gone, even with appendfsync always on the old primary. That is the real reason Redis is not the seat store (§8).

Say it

"The queue store runs AOF everysec plus a replica. The worst case is losing about a second of joins. The signed queue tokens carry each fan's seq, so I can re-seed next:{e} from the highest seq seen since. Nobody pays twice, and nothing is sold twice."

8Replication and Sentinel

Replication mechanics

  • REPLICAOF host port. The primary streams its writes to replicas and acks the client first.
  • Full sync: RDB (diskless by default since 7.0) plus the writes buffered meanwhile. Partial resync after a blip: PSYNC replid offset, if the gap still fits in repl-backlog-size (default 1 MB; size it for ~60 s of writes).
  • WAIT n ms blocks the caller until n replicas acked and returns how many did. It doesn't undo the write on timeout.
  • min-replicas-to-write 1 + min-replicas-max-lag 10: an isolated primary refuses writes after ~10 s, which bounds split-brain loss.
  • Replica reads are stale by ms to seconds. That's fine for ZRANK after T0 (the lobby is frozen), and a stale admittedUpTo is safe because the pointer only grows: a stale read can delay admission but never admit early.

Sentinel

  • At least 3 Sentinel processes on separate hosts monitor the primary.
  • One Sentinel marks it SDOWN (subjectively down) after down-after-milliseconds; ODOWN (objectively down) when quorum Sentinels agree.
  • A majority of Sentinels elects a leader, which promotes the best replica (priority, then the largest replication offset), repoints the others and publishes the new address.
  • Clients ask Sentinel get-master-addr-by-name and reconnect on a switch message.
  • Sentinel = HA for one shard. Cluster = sharding plus built-in failover; you don't run both.
Say it

"Redis replication is asynchronous, so failover can lose acknowledged writes. WAIT narrows the window but isn't consensus. That's why seat state is in PostgreSQL with a synchronous standby."

9Redis Cluster: slots, hash tags, hot keys

  • 16,384 hash slots; slot = CRC16(key) mod 16384. Each primary owns slot ranges; each has replicas.
  • Hash tags: if a key contains {…} with something inside, only that part is hashed, and only the first tag counts. admitted:{evt-7731}:{user-48213} lands in slot 500 with the rest of the event.
  • Multi-key commands, MULTI and scripts must stay in one slot, or you get CROSSSLOT.
  • MOVED = the slot lives elsewhere permanently: update the map. ASK = a slot is mid-migration: send ASKING plus the command to the target once, and keep the map.
  • Nodes gossip on the cluster bus (port + 10000). PFAIL → FAIL needs a majority of primaries; replicas are promoted by their vote. cluster-node-timeout (default 15 s) bounds both unavailability and how long a minority-side primary keeps accepting writes it will lose.
  • Resharding is online: per-key MIGRATE, or whole-slot atomic slot migration (Redis 8.4 CLUSTER MIGRATION; also in Valkey 9).
  • Cluster has only database 0, and no strong consistency.
Hot key: one mega event = one slot = one node = one thread

At T0, ~50,000 queue/me calls per second hit one sorted set. Mitigations, in order:

  1. Shed before Redis: the CDN absorbs polling; 0–20 s client jitter flattens queue/me.
  2. Make it O(1): precompute seqOf:{e} with one ZRANGE walk in chunks of 10,000, so queue/me becomes HGET.
  3. Read replicas (READONLY). Safe here because after T0 the lobby sorted set never changes.
  4. Pin the slot to its own node the day before. On-sales are scheduled, so place them, don't react.
  5. Split counters (key#0…#N, sum on read) for write-hot counters. Not needed here: the pointer moves once a second.
Trap

"Just add nodes" doesn't help a hot key: one key always lives on one node. Scaling out spreads events, not one event's load.

Why the join is a script, not two commands

The phase check and the write must be one step. Otherwise a join that read LOBBY could write into the lobby after open_queue.lua took ZCARD. Every lobby fan behind it would shift back one place, and the last one would collide with the first late arrival at seq n+1. Inside one script, a join lands cleanly on one side of the flip.

Why SET … NX EX 600 at admission

It makes admission idempotent: the first call wins and stores the token id; a retry finds the key and returns the same token, never a fresh 10 minutes. The TTL frees the slot by itself.

10.2 The admission controller's lease, with the fence inside the script

Exactly one controller instance may move an event's pointer. It holds a lease: SET leader:{e} <instanceId> NX PX 3000, renewed every second with a compare-and-extend. Because the lease and the pointer share the {e} slot, advance.lua can check the lease in the same atomic step. A paused ex-leader that wakes up can't move the pointer, which is the fencing check done right where the write happens.

-- acquire: any instance tries every second
SET leader:{e} <myId> NX PX 3000

-- renew.lua   KEYS: leader:{e}
--             ARGV: myId, ttlMs
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0          -- lease lost: stop ticking
-- advance.lua (SD-47) + the fence
-- KEYS: admittedUpTo, next, rate, soldOut,
--       leader            (all tagged {e})
-- ARGV: n, rate, soldOut, myId
local function num(k)
  return tonumber(redis.call('GET', k) or '0')
end
if redis.call('GET', KEYS[5]) ~= ARGV[4] then
  return -1                -- not the leader
end
local new = math.min(num(KEYS[1]) + ARGV[1],
                     num(KEYS[2]))
redis.call('SET', KEYS[1], new)
redis.call('SET', KEYS[3], ARGV[2])
redis.call('SET', KEYS[4], ARGV[3])
return new

10.3 Versioned seat-map snapshots

// builder, once a second per dirty event (the Kafka offset doubles as the version)
SET map:{e}:813 <6.25 KB> EX 120          ① bytes first
SET map:{e}:v 813                          ② then the pointer
// reader:  v = GET map:{e}:v ; if v == client's v → 304 ; else GET map:{e}:<v> → 200
Alternatives you should be able to compare

A live bitmap (SETBIT on every hold, plus INCR of a version in the same MULTI) is simpler but gives ~50 versions a second, so almost no 304s, and it puts Redis writes on the hold path. One key holding version + bytes saves a round trip but every check costs 6 KB. Pub/Sub or SSE deltas to 10,000 admitted fans is a phase-2 upgrade. SD-47's "≤ 1 version a second" is the sweet spot.

10.4 "Why not hold seats in Redis?" The question you will get

It's tempting: an all-or-nothing hold is one command on 8.4+, or a short script anywhere.

-- 8.4+: set all keys only if none exist
MSETEX 2 seat:{e}:101 h-5521
         seat:{e}:102 h-5521 NX PX 300000

-- any version: hold.lua
-- KEYS: seat:{e}:<id> …   ARGV: holdId, ttlMs
for i = 1, #KEYS do
  if redis.call('EXISTS', KEYS[i]) == 1 then
    return 0                -- one is taken
  end
end
for i = 1, #KEYS do
  redis.call('SET', KEYS[i], ARGV[1],
             'PX', ARGV[2])
end
return 1

Why it's rejected as the source of truth: Figure 8. The primary acks the hold, dies before the replica has it, the replica is promoted, and seat 101 is free again: an oversell. The hold path only does 50–500 writes a second, which PostgreSQL handles easily, so there's nothing to gain for that risk.

Where Redis does help: as a fast-reject gate in front of the database in a flash sale without a waiting room: DECRBY avail:{e}:A 2; if the result is negative, INCRBY it back and return 409 without touching PostgreSQL. The gate may be wrong in the safe direction; the database claim stays authoritative and UNIQUE(event, seat) is the last line.

If the interviewer insists on Redis semantics: a durable Redis-compatible store such as Amazon MemoryDB, which acknowledges a write only after a multi-AZ transaction log commits.

-- token_bucket.lua   KEYS: tb:{u}
-- ARGV: ratePerSec, burst, cost
local t     = redis.call('TIME')  -- server clock
local now   = t[1]*1000 + math.floor(t[2]/1000)
local rate  = tonumber(ARGV[1])
local burst = tonumber(ARGV[2])
local cost  = tonumber(ARGV[3])
local h = redis.call('HMGET', KEYS[1],
                    'tokens', 'ts')
local tokens = tonumber(h[1]) or burst
local ts     = tonumber(h[2]) or now
tokens = math.min(burst,
  tokens + (now - ts) / 1000 * rate)
local ok = tokens >= cost
if ok then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens,
           'ts', now)
redis.call('PEXPIRE', KEYS[1],
           math.ceil(burst / rate * 1000))
return ok and 1 or 0

10.7 Delayed jobs: a hold-expiry due queue

ZADD holds:due:{e} <expiresAtMs> h-5521
ZRANGE holds:due:{e} -inf <nowMs> BYSCORE
       LIMIT 0 100
ZREM holds:due:{e} h-5521
  → 1  I own it: release the hold
  → 0  another worker already got it

Score = due time, so "what's due?" is one range read. ZREM's return value is the claim, so several workers never release the same hold twice. SD-47's sweeper uses a partial index instead; both are valid.

10.8 Distributed locks, done right

SET lock:{e}:sweeper <uuid> NX PX 30000
-- release only if it's still mine (Lua):
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
-- 8.4+, no Lua needed:
DELEX lock:{e}:sweeper IFEQ <uuid>
Redlock, and the critique

Redlock acquires the same lock on a majority of N (usually 5) independent primaries, within a validity time of TTL minus elapsed time minus clock drift. Kleppmann's critique: it depends on bounded pauses and clock behaviour, and it issues no fencing token, so a GC pause still breaks it. Antirez's reply: with sane clocks and a check of the elapsed time it's safe enough for many uses. The interview answer is to avoid needing the argument at all.

Say it

"I'd use a Redis lock for efficiency, like making sure one sweeper runs, not for correctness. Correctness comes from a fencing check in the system of record: the conditional UPDATE … WHERE state = 'AVAILABLE', a version column, or the lease check inside the same Redis script that does the write."

Invalidation traps
  • Delete, don't set, on write. Two writers that each "update the DB, then SET the cache" can finish in the opposite order and leave the older value cached.
  • The race that remains (a reader repopulates the old value just before the DB commit) is closed by a short TTL or a delayed second DEL.
  • For ordered invalidations, drive them from CDC (the outbox/Debezium stream), not from application code.
What to cache in ticketing, and where

Immutable (venue layout, images): the CDN, versioned URLs, cached for a year. Shared and slowly changing (event page, prices): Redis cache-aside with jitter. Live but tolerant (availability): versioned snapshots (§10.3). Authoritative (claims, orders): never cached for decisions.

Client-side traps
  • Serializer mismatch: the default RedisTemplate uses JDK serialization, so "42" isn't stored as 42 and Lua's tonumber returns nil. Use StringRedisTemplate.

What Redisson's RLock does underneath

A hash per lock (owner id → re-entry count) with PEXPIRE, acquired by a Lua script; waiters subscribe to a Pub/Sub channel to learn when it's released; a watchdog renews the TTL. It's re-entrant and convenient, and it still has the Figure 12 problem, so the same rule applies: fence in the system of record.

16Rapid-fire interview drill

Cover the answer, say yours out loud, then compare. Each answer is a sentence or two, which is the length the room wants.

Redis is single-threaded. How is it fast?
The data is in RAM, commands are O(1)/O(log n), and there are no locks or context switches. Network I/O can use extra threads; execution stays on one thread, which is also why each command is atomic.
Is Redis durable?
Per node, with AOF everysec you lose up to ~1 s on a crash. Across a failover, async replication can lose acknowledged writes. WAIT narrows that but isn't consensus.
So why not keep seats in Redis?
A lost acknowledged hold is an oversell. The write path is only 50–500/s after the queue, so PostgreSQL's row locks and sync replica cost nothing at that rate.
MULTI vs Lua?
MULTI runs queued commands back-to-back but can't branch on a read and doesn't roll back. Lua can read, decide and write atomically. I use Lua for anything conditional.
What does WATCH do?
Optimistic locking: if a watched key changes before EXEC, EXEC returns nil and you retry. Good under low contention; under high contention a script is better.
How does Cluster decide where a key lives?
CRC16 of the key, or of its first {hash tag}, mod 16,384 gives the slot; each primary owns slot ranges. Wrong node → MOVED; slot mid-migration → ASK.
Why {event_id} in every key?
So one event's keys share a slot. Scripts and multi-key commands must stay in one slot, and different events still spread across nodes.
One event is too hot for its node. Now what?
Shed before Redis (CDN, jitter), make the hot call O(1) (precomputed seqOf), read from replicas (the lobby is frozen after T0), and pin the slot to its own node ahead of the sale.
What happens when the primary dies?
Sentinel or the Cluster's primaries detect it, a majority agrees, and the replica with the most data is promoted. Clients follow the new address. The last unreplicated writes are lost.
Is a Redis lock safe?
For efficiency, yes: SET NX PX plus a compare-and-delete release. For correctness, no: a paused client outlives its lease. You need a fencing token checked by the storage.
How do keys expire?
Passively on access, and actively by a sampling cycle about 10 times a second. Expired keys are never returned, but the expired notification can arrive late.
Which eviction policy for the queue store?
noeviction: it's state, not cache. A full store should refuse writes loudly, not silently drop places in line. Caches get allkeys-lfu on separate nodes.
Pub/Sub vs Streams?
Pub/Sub is fire-and-forget: offline means missed. Streams store entries and have consumer groups, acks and a pending list. For the durable seat-event log I use Kafka.
How do you rate-limit per user?
A token bucket in a hash, updated by one Lua script using server TIME, or INCR + EXPIRE NX for a fixed window. Fail open if Redis is down; the waiting room still meters the shop.
How do you prevent a cache stampede?
TTL jitter, one rebuilder per key via SET lock NX PX, serve stale while it refreshes, cache negatives briefly, and refresh hot keys early.
Pipelining vs transactions?
Pipelining saves round trips but isn't atomic. Transactions are atomic but still cost a round trip per command unless you pipeline them too.
How big is the lobby?
About 100 bytes per member: ~100 MB for a million fans, on one node.
What would you monitor?
Main-thread CPU, p99 latency and slowlog, memory vs maxmemory, evictions (zero on state stores), replication lag, fork time and persistence status.
What if Redis is down at T0?
Joins fail closed with 503 and Retry-After, and the CDN keeps serving the last queue state (stale-if-error). Admitted fans keep shopping because the JWT is checked without Redis. After failover, re-seed next:{e} from the highest seq seen in tokens.
What if the T0 scheduler fires twice?
open_queue.lua checks the phase first and returns the existing next if it's already QUEUE, so the second run changes nothing. Make every scheduled script idempotent.
Redis crashes in the middle of a Lua script. What's left?
The script's writes go to the AOF and replicas wrapped in MULTI/EXEC, so a restart or a replica sees all of them or none. An error inside the script is different: writes made before it stay.
Why not Kafka for the waiting room?
The access pattern is "what's my position?" and "move the pointer by 33", not "consume the next message". A sorted set and a counter answer both in O(log n); a log would need a consumer walking a million join events.
How do you stop a fan being admitted twice?
SET admitted:{e}:{u} <jti> NX EX 600. The first call wins; a retry reads the key and gets the same token back, never a fresh 10 minutes.
One key per seat, or a bitmap?
50,000 keys cost ~3–5 MB and 50,000 reads for a map; a bitmap is 6.25 KB and one GET. Per-seat keys only make sense if each seat needs its own TTL, and then the hold belongs in PostgreSQL anyway.
"Best available" with Redis?
BITPOS on a per-section bitmap finds a free run to suggest; the claim still happens in PostgreSQL with the conditional UPDATE, and a 409 moves on to the next run.
Redis or Valkey?
Protocol-compatible for everything here. Valkey is BSD-licensed and cheaper on AWS; Redis 8 is AGPL/RSAL/SSPL with the query engine built in. I'd let the platform team's standard decide.
